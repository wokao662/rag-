# 个性化学习推荐系统路线图

## 项目目标

通过多轮对话逐步了解用户当前的学习目标、困难和约束，从学习策略知识库中召回合适的方法，并给出有来源、可解释、可反馈的个性化推荐。

**知识库的主体内容来自用户投稿。** 学习方法的正规研究文献极难获取，而项目的初心是让经过验证的好方法被传承下来。因为用户推荐始终不是权威，投稿必须经过人工审查；审查通过后先小范围投放，再依据真实反馈升降推荐度，持续偏低的予以归档。权威文献作为冷启动种子语料与对照基线，不是内容主体。详见 `architecture.md` 的《用户投稿与渐进投放》。

系统中的“用户画像 Agent”定位为学习访谈与推荐辅助工具，不是医疗或心理诊断工具。它可以发现信息缺失或前后矛盾并向用户确认，但不能判断用户是否说谎，也不能推断疾病、智力、人格等敏感属性。

## 当前已经完成

- 使用 Tika 提取文档，并提供文本清洗、策略整理和分块流程。
- 使用 SiliconFlow Embedding API 将最终 chunk 向量化。
- 使用 Qdrant 保存并检索学习策略向量。
- 使用 PostgreSQL 保存用户、会话、消息和用户画像。
- 从用户当前消息中抽取明确表达的结构化画像字段。
- 使用 Java 白名单、类型、范围和原文证据规则校验画像更新。
- 合并并持久化用户画像，保留证据消息 ID 和更新时间。
- 通过终端完成持久化的多轮画像对话测试。
- 初步加入对话画像 Agent，动态决定继续追问还是进入推荐。
- 对 Agent 的决定进行 Java 结构校验，并保留固定规则作为失败兜底。
- 将画像与推荐链路拆分为 Spring Boot 服务并暴露 HTTP API，统一使用 RFC 7807 ProblemDetail 错误响应。
- 完成推荐链路：画像生成检索文本、Qdrant 召回、聊天模型生成、Java 校验引用与结构。
- 提供 Web 聊天界面（Spring Boot 托管静态页面，零构建），支持多轮对话、会话历史与推荐卡片。
- 收集推荐反馈：`recommendation_feedback` 表，同一消息同一策略只保留最新一次反馈。
- 记录模型调用日志：`model_call_logs` 表，含任务类型、输入输出、耗时、状态与错误信息。
- 访问码机制：`access_codes` 表为空时不拦截（本地开发），发放访问码后一码一用户空间。

## 当前方案的临时性质

- 画像抽取和画像决策目前是两次独立的大模型调用，便于调试，但会增加延迟和费用。
- 当前模型使用 `Qwen/Qwen3-32B`；它只是开发期实现，不代表最终自研模型选型。
- 当前画像字段较少，主要覆盖目标、内容、困难、时间、截止期限、偏好和尝试过的方法。
- 当前完整度是简单字段计数，只用于观察，不应直接等同于画像质量。
- Agent 返回 `recommend` 后已接入 Qdrant 推荐链路，但召回不带任何元数据过滤：`architecture.md` 推荐流程第 4 步（适合人群、来源、审核状态、曝光范围）尚未实现，`reviewStatus` 为 `draft` 的内容目前直接对外服务。
- 当前命令行程序用于验证流程，不是最终产品界面。
- 知识库内容极薄：13 个策略共 107 个 chunk，正文总计约 4356 字符，平均每 chunk 41 字符，多为单句定义，缺少实施细节与证据。策略骨架本身是正确的（10/13 精确对应 Dunlosky 等人 2013 年评估的十项技术，chunkType 分为 definition/procedure/suitable_condition/unsuitable_condition），缺的只是内容深度。
- 无 `strategies`、`sources`、`strategy_chunks` 表，策略数据仅存在于 `data/strategies/*.json` 与 Qdrant payload。用户投稿与人工审核队列缺少存储层，无法在 JSON 文件上实现（无事务、无审计、并发写入会丢数据、容器文件系统不可写）。
- `reviewStatus` 取值不一致：数据统一为 `draft`，`architecture.md` 此前定义为 `pending`/`approved`/`rejected`，两者无交集。
- 推荐度六个字段中 `triedCount`/`helpfulCount` 全库为 0 且无代码写入，`communityScore` 的换算关系未定义，Java 侧不读取其中任何一个。
- `QdrantClient.findByStrategyIds` 使用 scroll 且 `limit` 固定为 100、未处理分页，单个策略超过 100 个 chunk 时会静默截断。语料填厚后必然触发，且无错误无日志。
- 反馈只有 `adopted`/`dismissed` 两档，原计划的收藏、评分、执行结果未实现；缺少执行后反馈意味着无法验证方法是否真的有效。
- 没有审核者角色：`access_codes` 表无 role 列，所有测试者平权。
- 无限流机制，公网部署后存在被脚本刷 token 的风险。

## 开发阶段

### 阶段 1：学习策略知识库（已完成基础版本）

- 确定策略、具体方法、适合人群、来源和推荐度的数据结构。
- 完成文档提取、清洗、分块、Embedding 和 Qdrant 入库。
- 完成基础相似度检索与 RAG 推荐测试。

### 阶段 2：用户画像基础流水线（已完成基础版本）

- 建立 PostgreSQL 数据表和 Java Repository。
- 保存多轮对话和结构化画像。
- 实现画像抽取、校验、合并、完整度判断和固定追问。

### 阶段 3：对话画像 Agent（已完成基础版本）

- 根据画像和最近对话动态判断信息是否足够。
- 每轮只提出一个信息价值最高的问题。
- 识别前后信息冲突，并使用中性措辞请求用户确认。
- 防止重复追问、无限追问和越界推断。
- 将模型输出、决策理由、置信度和异常情况记录为可观察数据。
- 为模型输出增加自动化测试和典型对话评测集。

建议分支：`feature/conversational-profile-agent`

### 阶段 4：后端 API（已完成）

- 将终端流程拆分为业务服务，并用 Spring Boot 暴露 HTTP API。
- 提供用户、会话、发送消息、读取画像和获取推荐等接口。
- 增加统一错误处理、参数校验、日志和配置管理。
- API Key 只保存在服务端环境变量或密钥服务中，不返回给 Web 前端。

建议分支：`feature/spring-boot-api`

### 阶段 5：Web 聊天界面（已完成基础版本）

- 实现多轮聊天、会话历史和推荐结果展示。
- 展示方法名称、具体步骤、推荐理由和来源。
- 明确区分“用户确认”和“模型推测”。**原计划的“允许用户更正画像信息”已取消**：开放手动编辑等于完全采信用户自述，与“信用户的话只信一半”策略冲突；用户可查看画像并通过对话确认模型的推测（写入 `confirmed` 层级），但不能直接改写字段值。
- 收集采纳、跳过、收藏、评分和执行结果等反馈。（当前仅实现采纳与跳过；执行结果反馈对验证方法是否真正有效是决定性的，尚未实现。）

建议分支：`feature/web-chat-ui`

### 阶段 6：知识库存储层与用户投稿审核

这是“语料主体来自用户投稿”战略的地基，必须先于适合人群预测模型。没有存储层就无法建审核队列，也无法实现渐进投放。

- 新增迁移建立 `sources`、`strategies`、`strategy_chunks` 表，承载投稿原文、提交者、模型初判结果、审核状态、审核者、审核时间、驳回原因、六个推荐度字段与曝光范围状态。
- 统一 `reviewStatus` 取值，并迁移现有 13 个策略的 `draft`。
- 新增 `user_submission` 来源类型，使用户投稿能通过 `sourceIds` 非空校验。
- 在检索侧补齐元数据过滤：审核状态、曝光范围、适合人群、来源。这一步同时是审核闸门与渐进投放的载体。
- 定义审核者角色与权限（`access_codes` 加 role 列或另建管理员凭证）。
- Web 界面增加投稿入口；投稿接口纳入 `/api/v1/users/{externalId}/` 前缀以复用现有访问码过滤器，避免公网匿名提交。
- 模型初判不在提交时同步执行，改为队列或审核者点开时触发，并加投稿频率限制。
- 审核界面：待审核列表、展示模型初判与推荐度、通过/驳回/修改，并单独记录审核者判断（与模型 `predictedScore` 的差值即适合人群预测模型的训练标签）。
- 审核通过后自动 Embedding 并写入 Qdrant；重复入库前先按 `strategyId` 清理旧向量，避免孤儿点。
- 把现有 13 个策略审核通过，作为第一批标注数据与种子语料。
- 实现渐进投放与反馈驱动的升降权，包含最小反馈门槛与对小样本保守的估计；归档为软删除。

建议分支：`feature/strategy-submission-review`

**前置约束**：本阶段包含数据库迁移，按项目 Flyway 约定（不开启 `out-of-order`）必须晚于所有更低版本号的迁移分支合并，且后续分支应从其后切出。

**待定参数**：曝光机制、最小反馈门槛、升降权速度是否不对称、归档是否人工确认、是否增加执行后反馈档位、投稿者能否查看自己投稿的状态。这些参数直接影响表结构，需在建表前确定。

### 阶段 7：学习策略适合人群预测模型

这个模型工作在知识库入库侧。输入一条学习策略的名称、原理和具体做法，输出该策略可能适合的人群标签、适用问题、限制条件和初始推荐分。它解决的是“这条方法通常适合谁”，不是“当前用户到底是谁”。

- 先定义稳定的标签体系，例如记忆困难、理解困难、时间碎片化、备考期限紧张等。
- 以经过人工审核的学习策略及其适合人群作为训练和评测数据。
- 模型输出候选标签、置信度、判断依据和模型版本，不能直接覆盖人工数据。
- 正规来源中的明确描述优先于模型预测；模型主要补充缺失字段。
- 用户投稿的方法先进入待审核状态，由模型预标注，再结合来源审核和真实反馈决定是否发布（一律人审，无自动通过通道）。
- 人工确认后的标签写入策略元数据，供 Qdrant 过滤和后续排序使用。
- 推荐度需要区分模型给出的初始分和用户反馈形成的实际效果分，不能混成一个字段。
- 模型预测失败时仍允许保存原始策略，但不得把无依据的标签当成确定事实。

建议分支：`feature/strategy-audience-prediction`

### 阶段 8：检索与推荐排序

- 使用用户画像构造 Qdrant 查询，并应用适合人群等元数据过滤。
- 对向量召回结果进行简单可解释打分。
- 使用线上反馈评估召回率、相关性和推荐效果。
- 有足够真实数据后，再训练独立的推荐排序模型。

建议分支：`feature/recommendation-ranking`

### 阶段 9：自研用户画像模型

模型一的目标是画出用户**真实**画像，而不只是把用户说的话抄进字段。用户自述普遍是主观的，甚至存在“客观上说谎但主观上觉得没问题”的无意识失真（非恶意撒谎，是自我认知偏差），因此模型必须能觉察失真并主动探测。职责分解（2026-09-10 用户确认，取代此前“画像更新 / 信息充分性判断 / 冲突识别 / 追问策略”的四项说法）：

1. **画像判别与更新**：在对话中精准判断真实画像，输出字段时带来源层级标注（explicit / observed / inferred / confirmed / conflicting）。
2. **自述失真觉察**：识别自述与客观现实的矛盾，前后自述矛盾只是其中的特例。注意无意识失真在对话内部往往完全自洽，只有与行为观测对照才显形。
3. **验证式询问策略生成**：为可疑字段生成间接探测问法（行为回溯、具体化、时间线重建、锚定对比等心理学技法），一步步引导用户逼近真相；**措辞归聊天模型**，模型一只输出策略与意图。心理学知识落地为可审核、可积累的“询问策略库”，模型一负责选择与组合，而非自由发挥。
4. **充分性判断**：画像是否足够触发推荐，作为推荐闸门保留。

**v1 输入范围（隐私决定）**：只给对话相关内容——当前消息、历史画像（带层级）、过往询问策略及其结果，**不含行为观测 observed**。代价是觉察能力退化为仅能抓对话内部矛盾；作为冷启动 v1 可接受，作为终态可惜，待自研模型立项时结合留存数据重新评估。

**采集与使用解耦**：observed 现在照采并存本库，但不进模型一输入、不进 `model_call_logs`，因此不产生额外隐私暴露；将来若接入，只给确定性代码算出的聚合偏差信号（如“自述 60 分钟/天 vs 近 7 天实际中位数 6 分钟”），不给原始行为日志。

**字段分类**：可验证 claim（可用时间、学习频率、方法执行、坚持程度）才做失真觉察；主观 truth（学习目标、偏好、感受）直接采信，不为它设计探测问题，否则模型会变成审问。

**透明化**：先做，但文案必须与能力同步——v1 只承诺“通过多轮对话逐步了解你”，不提及行为校准；接入行为信号时同步更新文案。用户对隐私敏感，看到与实际不符的说明会直接流失。

**训练数据**：`model_call_logs` 的 `input_json` 是最大隐私暴露面（它会把模型输入原文存下来当训练数据），脱敏与保留期须单独落实；`status='fallback'` 的行与 confirmed 层级的对照样本是价值最高的训练标签。

- 建立经过脱敏和授权的训练或评测数据集；测试者对话用于训练是否需要单独同意，属合规问题，须先定。
- 先以独立模型服务接入，不直接重写数据库和 RAG 模块。
- 使用稳定的 JSON 契约替换当前第三方聊天模型调用。现有 `UserProfileExtractor` 与 `ConversationalProfileAgent` 是两个独立类、独立 Prompt，可逐个替换；但替换时须把“判断 + 策略”与“措辞”拆成两层（模型一出策略，聊天模型出话），替换边界比单纯换 Prompt 更深一刀。
- 保留 Java 校验、超时、降级和人工可纠正机制。

建议分支：`feature/profile-model-integration`

## 暂不优先

- 在缺乏真实用户反馈前训练复杂的推荐排序模型。
- 在适合人群标签尚未稳定前训练人群预测模型。
- 让一个模型同时承担画像、召回、排序、最终回复等所有职责。
- 仅靠 Prompt 代替 Java 数据校验和安全边界。
- 通过删除 Docker volume 的方式修改数据库结构。
- **在种子语料就绪前开放用户投稿**：库内容过少时推荐质量差，用户不会愿意贡献，飞轮无法启动。
- **用裸反馈比率直接驱动推荐度升降**：小样本下波动剧烈，会在拿到有意义的数据前误杀好方法。应设最小反馈门槛并使用对小样本保守的估计（如 Wilson score 下界）。
- **让模型直接生成 chunk 与 chunkId**：会破坏确定性 ID 的幂等性、产生 Qdrant 孤儿点，并损害语料文体一致性。
- **硬删除被降权的投稿**：负样本是适合人群预测模型的训练数据，且硬删后同样内容重投会与确定性 chunkId 冲突。
- **以 `docs` 文档作为用户意图的权威来源**：本项目经多手 AI 接力，文档中混有未经用户确认的推断内容。优先级为：用户当前陈述 > 代码与数据库实测 > 文档。

## 协作约定

- 一个分支尽量只完成一个阶段目标。
- 合并前运行编译、自动化测试和关键手动测试。
- 重要设计写入 `docs`；具体开发项可建立 GitHub Issue。
- 短期实现细节可以使用代码 `TODO`，但不能只依赖聊天记录保存决策。
- `.env`、API Key、数据库密码和本地生成数据不提交到 Git。
