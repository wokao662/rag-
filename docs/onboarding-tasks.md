# 新手任务卡（Onboarding Tasks）

这份文件给刚加入、对架构和前后端还不熟悉的协作者，以及协助他的 AI。五个任务按顺序排列，从零代码风险到需要判断力。每个任务自包含：读对应那一节就够开工，不需要口头转述。

## 怎么用这份文件

**先读上下文包，再碰任何任务：**

1. `README.md` —— 怎么跑起来、有哪些接口、约定是什么
2. `docs/architecture.md` —— 系统现在长什么样、每个模型负责什么
3. `docs/roadmap.md` —— 做到哪了、接下来做什么、哪些明确不做

**总则（每个任务都适用）：**

1. 一个任务一个分支，分支名用 `task/<序号>-<短描述>`，从最新 `main` 切出。
2. **先笔记后动手**：动手前先交一段文字，写清"我读了哪些文件、我理解这个任务要解决什么、我打算怎么验证做完了"。这段文字通过 review 之后才允许改文件。这一步不是形式主义，它挡住大多数"AI 代写但方向错了"的返工。
3. 小步提交，每次提交只做一件事。
4. PR 描述必须写两段：改了什么、**怎么验证的**（跑了什么命令、看到什么输出）。没有验证记录的 PR 会被打回。
5. 卡住超过一小时没有进展，停下来问，不要继续猜。猜错的代价比问一句大得多。
6. 不在任务范围里的"顺手优化"一律不做。看到想改的东西，记在 PR 描述里提出来，由维护者决定。

## 任务 ① 对话评测集

**目标**：建一个小型对话评测集，覆盖四类对话：信息不足、一次说清、前后矛盾、拒绝回答。

**为什么重要**：系统靠多轮对话攒画像，画像充足（`ready=true`）才触发推荐。现在没有任何用例能回答"对话行为对不对"这个问题。这份评测集是将来替换自研画像模型时的评测地基——没有它，换模型只能靠感觉。

**必读**：`docs/roadmap.md` 近期优先任务第 9 条；`docs/architecture.md` 的画像与对话章节；`README.md` 的 Web 界面与推荐 API 两节。

**怎么做**：

1. 对着维护者提供的共享测试环境对话（地址见部署手册或团队公告）。该环境未就绪时，先按 `docs/architecture.md` 与 `docs/roadmap.md` 写用例草稿，把“跑系统验证实际行为”留到环境就绪后补——本任务不要求本地跑起系统：本地跑需要 Docker，而 Docker 不是每个人的环境里都有。
2. 亲自聊至少十轮，观察：助手什么时候追问、什么时候出推荐卡片、右侧画像抽屉里哪些字段出现了、每个字段带的“你说过”引用对不对。
3. 按四类各写若干用例。每条用例包含：对话脚本（用户逐句说什么）、期望结果（该继续追问 / 该出推荐 / 该识别出矛盾并确认）、期望画像字段及其值。
4. "前后矛盾"类至少包含一条时间类矛盾（先说每天 30 分钟，后说工作日有两小时），观察系统是否发现并确认，而不是直接覆盖旧值。
5. "拒绝回答"类观察系统是否能在信息缺失时继续对话而不是编造画像。

**done 的定义**：一个 JSONL 文件（建议放 `data/eval/`），每行一条用例，字段含 `id`、`category`、`turns`（用户话语数组）、`expect`（期望行为与画像字段）。四类都有覆盖，总数不少于 12 条。

**禁止**：不改任何代码；不为凑数写雷同用例；期望值不许写"应该合理"这类无法判定的描述——必须写成能对照输出判断真假的断言。

**验收方式**：维护者抽三条用例真跑一遍对话，对照期望是否可判定。

## 任务 ② 文献调研清单

**目标**：调研支撑种子语料的文献，产出一份带出处的清单。

**为什么重要**：库里的学习方法需要有证据支撑，`evidenceScore` 字段就是干这个的。团队一直苦于找不到相关文献，这份清单直接缓解这个瓶颈。

**必读**：`docs/architecture.md` 的推荐度字段章节；`data/strategies/` 下任意两个 JSON，理解一个策略长什么样；`generate_strategy_chunks.py` 开头注释，理解 sourceIds 的作用。

**怎么做**：

1. 调研方向：学习策略有效性的实证研究（如分散练习、检索练习、交错练习这类已被验证的策略），以及中文学习者场景的适用性讨论。
2. 每篇文献产出：出处（作者/年份/标题/链接）、核心结论一句话、可提取要点（能变成策略定义或步骤的部分）、建议归属到哪个现有策略（或建议新建策略）。
3. 区分两类文献：能直接支撑某个策略有效性的（进 `evidenceScore` 依据），和只描述适用人群的（进适合人群标签依据）。

**done 的定义**：一份 Markdown 清单，不少于 8 篇，每篇含上述四要素，出处可点开验证。

**禁止**：不收录无法验证出处的内容；不抄全文进仓库（只记要点与出处，版权与体积都不允许）。

**验收方式**：维护者抽查三篇出处是否真实存在、要点是否忠于原文结论。

## 任务 ③ 13 个策略的审核预填

**目标**：为现有 13 个策略做审核预填：核对来源、抽查 chunk 质量、写适合人群标签初稿。

**为什么重要**：这 13 个策略现在全是 `draft` 状态却已在对外服务，与新投稿"审核通过才入库"的标准双标。审完它们既形成第一批标注数据，也充当冷启动种子。审核界面还没做，预填可以先以数据整理形式推进。

**必读**：`data/strategies/` 全部 13 个 JSON；`data/chunks/` 下对应的 JSONL；`docs/architecture.md` 的适合人群预测章节；`docs/roadmap.md` 近期优先任务第 3 条。

**怎么做**：

1. 逐个策略核对 `sourceIds` 是否真实指向 `data/sources/` 里存在的来源，来源内容是否真的支撑该策略。
2. 抽查每个策略的 chunk：正文是否自包含（单独读一个 chunk 能懂）、是否有截断或重复。
3. 为每个策略写适合人群标签初稿（如：记忆困难、时间碎片化、备考期限紧张），以及不适用人群，各附一句理由。
4. 把发现的问题（来源缺失、chunk 质量差、标签拿不准）单独列一张问题表，不要自己悄悄改。

**done 的定义**：13 份预填表（建议 `data/review/<strategyId>.md`）+ 一张问题表。

**禁止**：**只写预填表，不改 `data/strategies/*.json`、不重跑 `generate_strategy_chunks.py`、不碰 Qdrant。** 入库与重跑由维护者指导后进行——改 JSON 不重跑入库会造成库与文件不一致，重跑时机错了会产生孤儿向量。

**验收方式**：维护者对照问题表逐条确认，并决定哪些预填可以转正。

## 任务 ④ 默认包旧命令行类清理

**目标**：处理 `src/main/java/` 根目录（默认包）下的 5 个旧类：`Database`、`DocumentExtractor`、`DatabaseConnectionTest`、`LLMTest`、`UserProfileConversationTest`。

**为什么重要**：它们在默认包，命名包里的代码引用不到它们（Java 语言限制），属于历史遗留的命令行验证类。留着会误导后来者以为它们是主链路的一部分。

**环境要求**：只需 JDK 17 与 Maven。本仓库测试为 Web 层测试与纯单测（service 全部 mock），不启动数据库与 Flyway，因此不需要 Docker、不需要 PostgreSQL/Qdrant、不需要 API key。没有 WSL、装不了 Docker 的机器也能完成本任务。

**必读**：`README.md` 的 Spring Boot 后端一节（里面说明这些类"暂时保留用于验证模型和 RAG 链路"）；逐个打开这 5 个文件读 main 方法在做什么。

**怎么做**：

1. 对每个类先证明现状：grep 全仓库找引用者，记录"有无引用、被谁引用"。
2. 分类：完全无引用的死代码 → 删除；仍有验证价值但可搬移的 → 搬到合适的命名包并加注释说明用途；仍被脚本或文档引用的 → 不动，只在问题里记录。
3. 每删/搬一个类跑一次 `mvn test`，确认全绿。
4. 若 README 里"暂时保留"的说明因此过时，同步更新那句话。

**done 的定义**：5 个类各自有明确归宿（删/搬/留），`mvn test` 全绿，PR 描述里附每个类的引用证明与归宿理由。

**禁止**：不许凭"看起来没人用"就删——必须先给引用证明；不许改命名包里的任何主链路代码；不许动数据库迁移文件。

**验收方式**：维护者核对引用证明，并跑 `mvn test` 复验。

## 任务 ⑤ 部署手册与演练

**目标**：把项目部署到云服务器并启用访问码，全程记录成可复用手册。

**为什么重要**：部署是"做过一遍"和"看过十遍"的差别。手册让下一次部署不依赖任何个人的记忆。

**前置条件**：服务器已购买、凭据已就位。未就绪时不要开始本任务，先做前四个。

**必读**：`compose.yaml`；`README.md` 的 PostgreSQL 与团队协作约定两节；`docs/roadmap.md` 近期优先任务第 7 条。

**怎么做**：

1. 照流程部署：容器、数据库、Qdrant 卷、后端服务。
2. 启用访问码（数据库插入），验证未持码请求被拒、持码请求放行。
3. 记录每一步命令、每个踩到的坑、每个与 README 不符的地方。
4. 验证数据不丢：重启容器后用户与对话仍在；**手册里必须写明哪些命令会删数据、绝对不许跑**（如 `docker compose down -v`）。

**done 的定义**：一份部署手册（建议 `docs/deployment.md`），含前置条件、步骤、验证清单、危险命令清单；且实际部署环境可访问。

**禁止**：不在手册或提交里写任何凭据、密钥、访问码明文；不在生产库上跑本仓库的迁移做实验。

**验收方式**：维护者按手册从零复跑一遍能否成功。

## 明确禁止接触的范围

以下范围需要产品判断或不可逆操作，不在新手任务内，看到问题请记录不要动手：

- 数据库迁移文件（`src/main/resources/db/migration/`）：Flyway 迁移不可逆，顺序错了会卡死后续所有迁移
- 反馈与升降权逻辑（`recommendation` 包）：驱动推荐排序的核心，判断错了污染统计
- `model_call_logs` 的脱敏与保留期：隐私判断需要产品理解
- 前端核心交互（`static/app.js` 的对话与历史页逻辑）：UI 回归难发现
- 审核界面与投稿接口：依赖尚未定案的审核者身份设计

## 验收与 review 流程

1. 每个 PR 由维护者 review；review 意见分两类：必须改（方向或正确性）、建议改（风格或可选优化）。新手只需当场处理"必须改"。
2. 合并方式为 squash，一个 PR 进 main 一个提交；因此 PR 标题要能单独成立，写清做了什么。
3. 每完成一个任务，在本文档对应小节末尾追加一行完成记录：日期、分支名、PR 编号、一句话结论。让后来者知道哪些已经做完。
