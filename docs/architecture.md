# 个性化学习推荐系统架构

## 总体流程

```text
用户消息
  -> 保存消息到 PostgreSQL
  -> 画像信息抽取
  -> Java 证据与类型校验
  -> 合并用户画像并保留来源
  -> 对话画像 Agent 判断下一步
       -> 信息不足：生成一个追问并继续对话
       -> 信息足够：构造检索条件
  -> Embedding 将检索文本向量化
  -> Qdrant 召回学习策略 chunk
  -> 元数据过滤与推荐排序
  -> 大模型基于候选策略生成回答
  -> 保存推荐和用户反馈
  -> 后续更新画像及推荐效果数据
```

## 数据存储职责

### PostgreSQL

保存需要可靠关联、更新和审计的业务数据：

- `users`：用户身份标识。
- `conversations`：一次连续对话。
- `messages`：用户和助手的原始消息及消息元数据。
- `user_profiles`：当前结构化画像和完整度。
- 未来增加：推荐记录、用户反馈、画像历史版本和模型决策日志。

PostgreSQL 是用户和业务数据的主存储。用户画像不能只存在大模型上下文中。

### Qdrant

保存学习策略最终 chunk 的向量、可返回正文和检索元数据，用于语义召回：

- chunk 文本：策略名称、适用问题和具体做法等可检索内容。
- vector：Embedding 模型生成的向量。
- payload：`strategyId`、`sourceIds`、适合人群、来源类型、推荐度等元数据。

Qdrant 不负责保存完整用户会话，也不替代 PostgreSQL。

### Docker volume

- `qdrant_storage`：Qdrant 本地数据。
- `rag_postgres_data`：PostgreSQL 本地数据。

它们可以调整实际磁盘位置，但开发初期建议继续使用 Docker 命名卷，避免路径权限和跨电脑差异。需要迁移时应先备份，再统一修改 Compose 配置。

## 核心模块职责

### 画像抽取器

从当前用户消息中提取明确表达的结构化信息，不负责判断是否已经足够推荐，也不直接写数据库。

当前字段包括：

- `learningGoal`
- `learningContent`
- `mainDifficulty`
- `availableMinutesPerDay`
- `daysUntilDeadline`
- `preferredLearningStyle`
- `triedMethods`

每个字段需要包含值、来源类型、置信度和原文证据。

### 画像校验与合并

Java 负责不可交给 Prompt 单独保证的硬边界：

- 字段白名单。
- 数据类型和数值范围。
- 证据是否确实存在于当前消息。
- 来源类型是否合法。
- 不合法更新拒绝写入画像。

未来合并逻辑需要保存画像历史，而不是只覆盖旧值。

### 对话画像 Agent

负责需要语义判断的软决策：

- 当前信息能否支持初步推荐。
- 哪项缺失信息最可能改变推荐结果。
- 下一轮应该只询问什么。
- 最近消息之间是否存在需要确认的矛盾。

它不能负责：

- 判断用户是否说谎。
- 进行心理、医疗、智力或人格诊断。
- 绕过 Java 校验直接写数据库。
- 自己编造画像事实。
- 在用户不愿回答时无限追问。

### 本地决策守卫

`ProfileDecisionValidator` 校验 Agent 输出结构和基本一致性；`ProfileReadinessPolicy` 在模型接口失败、超时或输出不合法时提供确定性兜底。

长期应保留守卫和兜底，即使以后换成自研模型。

### 检索与推荐

Embedding 模型只负责把文本转换为向量。未来的用户画像模型不会替代 Embedding，也不会直接替代 Qdrant。

初期推荐流程：

1. 从画像生成检索查询。
2. 使用相同 Embedding 模型生成查询向量。
3. 在 Qdrant 使用 Cosine 相似度召回候选策略。
4. 使用适合人群、来源、审核状态和曝光范围过滤。
5. 使用简单规则综合相似度与推荐度排序。
6. 将候选 chunk 交给聊天模型组织成最终回复，并附带来源。

有足够反馈数据后，独立的排序模型可以替换第 5 步，但不替换 Embedding 和向量召回。

第 4 步同时是「渐进投放」的唯一实现位置：审核通过不等于对全部用户可见，新入库策略先只对少量用户曝光，反馈达标后才扩大范围（见《用户投稿与渐进投放》）。

当前实现状态：第 4 步尚未实现。`RecommendationService` 的向量召回不带任何元数据过滤，`findByStrategyIds` 也只按 `strategyId` 过滤，因此审核状态目前只是记录而不是闸门。

### 学习策略适合人群预测模型

该模型用于完善知识库中的学习策略元数据，主要处理新增或信息不完整的学习方法，尤其是用户投稿的自由文本——投稿不带整理好的结构化字段，需要模型先抽取再交由 Java 切块。

```text
学习策略名称、原理、具体步骤和来源
  -> 适合人群预测模型
  -> 候选人群标签、适用问题、限制条件、置信度和依据
  -> 模型同时输出结构化策略字段，由 Java 按固定模板确定性切 chunk
  -> Java Schema 校验
  -> 人工审核（用户投稿一律人审，不设自动通过通道）
  -> 写入策略元数据
  -> Embedding 向量化并进入 Qdrant
  -> 先小范围投放，按真实反馈调整推荐度
```

审核通过之后直到进入 Qdrant 为止是全自动流程，不再需要人工干预。

建议输出至少包含：

- `audienceTags`：适合人群标签。
- `problemTags`：主要解决的学习问题。
- `constraints`：不适合的情况或使用前提。
- `predictedScore`：模型给出的初始推荐分。
- `confidence`：对本次预测的置信度。
- `evidence`：来自策略正文或来源的判断依据。
- `modelVersion`：生成预测的模型版本。
- 结构化策略字段：`name`、`summary`、`steps`、`suitableFor`、`notSuitableFor`，供 Java 切块使用。

`reviewStatus` 的取值需要统一。当前 `data/strategies/*.json` 全部 13 个文件使用 `draft`，而本节此前定义的是 `pending`/`approved`/`rejected`，两套取值没有交集——按文档写筛选条件会一条都查不出来。这是待修正的缺陷。

**chunk 由 Java 生成，不由模型生成。** `chunkId` 依赖 `uuid5(固定命名空间, "{strategyId}:{chunkType}:{index}")` 确定性推导，这是重复入库不产生 Qdrant 孤儿点的前提。模型直接生成 chunk 会破坏幂等性，并使 chunk 文体与既有语料不一致而损害检索质量，还会让 `RecommendationValidator` 的 `citations` 校验失去稳定锚点。模型只负责输出结构化字段，切块套用现有四类模板：`definition`、`procedure`、`suitable_condition`、`unsuitable_condition`。

它与其他模型的职责不同：

| 模块 | 核心输入 | 核心输出 | 作用阶段 |
| --- | --- | --- | --- |
| 用户画像模型 | 用户消息和历史画像 | 当前用户特征与下一步追问 | 用户对话侧 |
| 适合人群预测模型 | 学习策略正文和来源 | 该策略通常适合的人群标签 | 知识库入库侧 |
| Embedding 模型 | 文本 | 向量 | 入库与检索侧 |
| 推荐排序模型 | 用户画像和候选策略 | 针对当前用户的候选顺序 | 在线推荐侧 |

适合人群预测模型不能替代 Embedding。它生成有业务含义的结构化元数据，Embedding 仍负责语义向量化。它也不直接替代推荐排序模型：一种方法“通常适合某类人”，不代表它一定是当前用户候选中的最佳方案。

### 推荐度字段与写入者

`data/strategies/*.json` 的 `recommendation` 对象已定义六个字段。关键不在于字段数量，而在于**每个字段只能有一个写入者**——只要写入者唯一，用户反馈就不会覆盖模型初判，模型版本之间也才可比较。

| 字段 | 含义 | 建议写入者 | 写入时机 |
| --- | --- | --- | --- |
| `evidenceScore` | 文献证据强度；用户投稿天然低 | 入库流程 | 按来源类型确定，之后不改 |
| `effectivenessScore` | 方法本身的有效性评价 | 人工审核者 | 审核时确定 |
| `communityScore` | 社区验证度；用户投稿的主要分数来源 | 反馈聚合任务 | 由 `triedCount`/`helpfulCount` 计算 |
| `triedCount` | 实际尝试过的人数 | 反馈聚合任务 | 用户提交执行反馈时累加 |
| `helpfulCount` | 认为有效的人数 | 反馈聚合任务 | 同上 |
| `overallScore` | 全局综合分 | 反馈聚合任务 | 由上述字段加权计算，反馈变化时重算 |

针对具体用户的临时排序分属于在线推荐阶段（阶段 8），不落入上表任何字段。

审核界面必须**同时展示模型给出的 `predictedScore`，并单独记录审核者自己的判断**。两者的差值就是适合人群预测模型最重要的训练标签；若共用一个字段，审核动作会覆盖模型初判，标签即被销毁。

当前缺口：`triedCount`/`helpfulCount` 全库为 0 且无任何代码写入；`communityScore` 与二者的换算关系（含最小样本量门槛）尚未定义；Java 侧不读取这六个字段中的任何一个。

此前本节曾建议 `predictedBaseScore`/`editorScore`/`feedbackScore`/`rankingScore` 四分体系，与数据实际字段不一致且未落地。四分体系并非错误，但它描述的职责已由上表六个字段承担；保留两套只会造成写入者不清。本节以数据实际字段为准。

## 用户投稿与渐进投放

知识库的主体内容来自用户投稿，而不是权威文献。原因是学习方法的正规研究文献极难获取，而项目的初心是让经过验证的好方法被传承下来。

权威文献（如 Dunlosky 等人 2013 年的综述）定位为**冷启动种子语料**：作用是让早期用户第一次使用就能得到有用的推荐，从而愿意贡献自己的方法；同时它 `evidenceScore` 高、可直接通过审核，为用户投稿提供同台竞争的对照基线。它不是内容主体。

### 投稿流程

```text
用户在 Web 界面提交自己的学习方法
  -> 模型初判：抽取结构化字段、预标注适合人群与推荐度
  -> Java 确定性切 chunk 并做 Schema 校验
  -> 进入待审核队列
  -> 人工审查：看方法本身、适合人群、模型生成的推荐度
  -> 驳回：记录原因，不入库
  -> 通过：全自动 Embedding 并写入 Qdrant，不再人工干预
  -> 小范围投放
  -> 按真实反馈调整推荐度
  -> 反馈持续偏低：进入待归档审查
```

用户投稿**一律经过人工审查，不设自动通过通道**。

人工审查只能过滤明显不合理的内容，方法是否真正有效必须靠投放后的真实反馈验证——这正是“审核通过”不等于“全量投放”的原因，也是本系统与普通内容审核的关键区别。

投稿没有权威来源，但入库流程硬校验 `sourceIds` 不能为空，因此需要新增一类来源（如 `user_submission`），其 `evidenceScore` 固定为低值。这也对应“正规来源中的明确描述优先于模型预测”的原则。

### 渐进投放

新入库策略先只对少量用户曝光，反馈达标后逐步扩大范围；反馈持续偏低则降权，低到一定程度进入待归档审查。

该机制只能在检索侧的元数据过滤层实现，因此召回必须带上审核状态与曝光范围条件。

**归档必须是软删除**：PostgreSQL 中保留完整记录并转为归档状态，仅从 Qdrant 移除向量以停止投放，并保留人工恢复入口。两个理由：

1. 被降权归档的投稿是适合人群预测模型最有价值的**负样本**。只学过成功案例的模型无法判断“看起来合理但实际无效”的方法。
2. `chunkId` 为确定性推导，硬删后同样内容重新投稿会生成相同 ID 并与历史记录冲突。

### 待定参数

以下参数会影响数据库表结构，需在实现前确定：

- 曝光机制：按比例随机曝光、按曝光人数上限，还是按用户分群。按人数上限的优势是能明确知道“样本已收齐、可以判断了”。
- 最小反馈门槛：反馈数低于该值时只累积不调整推荐度。
- 升权与降权的速度是否不对称。
- 归档由系统自动执行还是人工确认。
- 反馈是否增加“执行后反馈”档位。现有 `adopted`/`dismissed` 测的是用户愿不愿意试，不是试了有没有用；一个标题吸引人的无效方法可能采纳率很高。对“传承真正好的方法”这一目标而言，执行后反馈是决定性的。
- 投稿者能否查看自己投稿的状态与被采纳次数。这对投稿意愿是强激励，也最贴合传承的初心。

### 已知风险

**冷启动的双边市场问题**：库内容少 -> 推荐质量差 -> 用户不愿投稿 -> 库仍然少。种子语料必须先于投稿功能就绪。

**审核工作量会成为吞吐瓶颈**：投稿一律人审，且当前没有审核者角色概念（`access_codes` 表无 role 列，所有测试者平权），审核者数量为一。每条投稿需要判断方法、适合人群与模型推荐度是否有依据，投稿量上升后人工审核会先于技术能力达到上限。审核界面需为此优化（预填模型判断、批量操作），并考虑限制投稿速率。

**投稿接口是成本放大攻击面**：`AccessCodeFilter` 仅拦截 `^/api/v1/users/([^/]+)(?:/.*)?$`。若投稿接口命名为 `/api/v1/strategies/**`，则完全不受访问码保护，公网部署后任何人可提交并触发模型初判，刷爆 API 预算并用垃圾淹没审核队列。对策：投稿接口纳入 `/api/v1/users/{externalId}/` 前缀以复用现有过滤器；模型初判不在提交时同步执行，改为队列或审核者点开时触发；加投稿频率限制。

**小样本噪声会误杀好方法**：“少量投放”与“靠反馈升降权”组合会自然产生该问题。若投放给 5 人而前 2 人恰好都 `dismissed`，裸比率为 0%，一个好方法会在拿到任何有意义的数据之前被判死刑。对策：设最小反馈门槛、使用对小样本保守的估计（如 Wilson score 下界）而非裸比率、采用增量更新而非重算以避免单条反馈造成跳变。

## 用户画像的数据层级

未来画像不能把所有信息都当成同等可靠的事实，建议至少区分：

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| `explicit` | 用户明确表达 | “我每天只有 30 分钟” |
| `observed` | 系统从真实行为记录得到 | 连续三次未完成一小时计划 |
| `inferred` | 模型根据证据提出的待确认假设 | 可能更适合短时学习任务 |
| `confirmed` | 用户确认过的信息或推测 | 用户确认每天只能学习 30 分钟 |
| `conflicting` | 新旧证据暂时冲突 | 曾说 30 分钟，后来表示工作日有 2 小时 |

`inferred` 不能悄悄升级成事实。影响明显的推测应向用户确认；确认结果写入 `confirmed` 层级，而不是覆盖原字段值。

用户可以查看画像，但**不提供直接编辑或更正字段的入口**。理由是产品的核心策略为“信用户的话只信一半”：用户可能对自己的定位不清晰，画像应由模型基于行为与多轮对话逐步引出；开放手动编辑等于完全采信用户自述，与该策略直接冲突。据此取消 roadmap 阶段 5 中“允许用户更正画像信息”一项。注意这与来源层级不矛盾：模型推测经用户确认是允许的，用户不能直接改写字段值。

## 模型边界与替换方式

当前第三方聊天模型承担两个不同任务：

1. 从当前消息提取画像更新。
2. 根据画像和对话决定追问或推荐。

两个任务应保持独立接口，即使暂时使用同一个模型。未来自研用户画像模型只要遵循稳定的输入输出 JSON 契约，就可以替换这两个调用，而不需要重写 PostgreSQL、Java Repository、Qdrant 或 Web 页面。

推荐排序是另一个目标不同的模块。它的输入是用户画像和候选学习策略，输出是候选顺序或分数；不建议与对话画像模型强行合并。

适合人群预测也是独立任务。早期可以继续使用聊天模型配合严格 JSON Prompt 生成预标注；积累足够人工确认的数据后，再接入自己的深度学习模型。替换时应保持输入输出契约不变，让知识库处理代码不依赖某个具体模型。

## 未来后端边界

建议 Spring Boot 层逐步形成以下服务：

- `ConversationService`：会话与消息生命周期。
- `UserProfileService`：抽取、校验、合并和画像历史。
- `ProfileDialogueService`：充分性判断、冲突确认和追问。
- `StrategyRetrievalService`：Embedding、Qdrant 召回和过滤。
- `RecommendationService`：排序、答案生成、引用和结果保存。
- `FeedbackService`：用户反馈与效果数据。

Web 前端只调用后端 API，不直接访问 SiliconFlow、Qdrant 或 PostgreSQL。

## 安全、隐私与可观察性

- API Key 和数据库密码只通过环境变量或服务端密钥管理加载。
- 日志不记录密钥，也应避免直接记录不必要的敏感原文。
- 用户应能知道画像用于什么，并能查看或删除自己的画像数据。删除属隐私权利，与“不提供字段编辑入口”不冲突。
- 保存模型版本、Prompt 版本、决定结果、置信度、回退原因和耗时，方便评测与排错。
- 对超时、限流、JSON 不合法和数据库失败分别处理，不能把技术故障伪装成用户信息不足。
