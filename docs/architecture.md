# 个性化学习推荐系统架构

## 总体流程

```text
用户消息
  -> 保存消息到 PostgreSQL
  -> 画像信息抽取
  -> Java 证据与类型校验
  -> 合并用户画像并保留来源
  -> 对话画像 Agent 判断下一步
       -> 信息不足：生成一个追问并继续对话
       -> 信息足够：构造检索条件
  -> Embedding 将检索文本向量化
  -> Qdrant 召回学习策略 chunk
  -> 治理闸门过滤（无档案 / 待归档 / 已暂停 / 未审核 / 超出曝光人数上限）
  -> 按策略补齐 chunk
  -> 大模型基于候选策略生成回答
  -> 保存推荐和用户反馈，并记录曝光（去重）
  -> 事务提交后重算行为观测
  -> 尝试后反馈驱动社区分与投放档位重算
```

模型调用日志在写入前脱敏。行为观测只采集不使用，不进入任何模型输入（见《用户画像的数据层级》与《安全、隐私与可观察性》）。

## 数据存储职责

### PostgreSQL

保存需要可靠关联、更新和审计的业务数据：

- `users`：用户身份标识。
- `conversations`：一次连续对话。
- `messages`：用户和助手的原始消息及消息元数据。推荐结果以快照形式序列化进 `metadata_json`，因此方法后来被降权归档也不影响历史页回看。
- `user_profiles`：当前结构化画像和完整度。
- `recommendation_feedback`：卡片上的 👍，只汇总给投稿者看，不参与推荐度计算。
- `method_trial_feedback`：尝试后反馈，驱动升降权的**唯一**信号。
- `model_call_logs`：模型决策日志，含输入输出快照、耗时与 token 用量，写入前脱敏，按保留期自动清理。
- `access_codes`：测试期访问码，一个码对应一个独立用户空间。V9 起每个码带 `role`（`tester` / `reviewer`），角色属于码而不属于用户，由 `POST /api/v1/auth/redeem` 返回给前端。
- `strategies` / `sources` / `strategy_chunks` / `strategy_exposures`：策略存储层与曝光去重。
- `behavior_observations`：行为观测聚合值，只采集不使用。
- 未来增加：画像历史版本、投稿队列与审核审计。

PostgreSQL 是用户和业务数据的主存储。用户画像不能只存在大模型上下文中。策略档案的权威来源仍是 `data/strategies/*.json`，数据库是它的可事务镜像；`strategy_chunks` 同理是 Qdrant 内容的镜像，两边 `chunk_id` 一致。

### Qdrant

保存学习策略最终 chunk 的向量、可返回正文和检索元数据，用于语义召回：

- chunk 文本：策略名称、适用问题和具体做法等可检索内容。
- vector：Embedding 模型生成的向量。
- payload：`strategyId`、`sourceIds`、适合人群、来源类型、推荐度等元数据。

Qdrant 不负责保存完整用户会话，也不替代 PostgreSQL。

### Docker volume

- `qdrant_storage`：Qdrant 本地数据。
- `rag_postgres_data`：PostgreSQL 本地数据。

它们可以调整实际磁盘位置，但开发初期建议继续使用 Docker 命名卷，避免路径权限和跨电脑差异。需要迁移时应先备份，再统一修改 Compose 配置。

## 核心模块职责

### 画像抽取器

从当前用户消息中提取明确表达的结构化信息，不负责判断是否已经足够推荐，也不直接写数据库。

当前字段包括：

- `learningGoal`
- `learningContent`
- `mainDifficulty`
- `availableMinutesPerDay`
- `daysUntilDeadline`
- `preferredLearningStyle`
- `triedMethods`

每个字段需要包含值、来源类型、置信度和原文证据。

### 画像校验与合并

Java 负责不可交给 Prompt 单独保证的硬边界：

- 字段白名单。
- 数据类型和数值范围。
- 证据是否确实存在于当前消息。
- 来源类型是否合法。
- 不合法更新拒绝写入画像。

未来合并逻辑需要保存画像历史，而不是只覆盖旧值。

### 对话画像 Agent

负责需要语义判断的软决策：

- 当前信息能否支持初步推荐。
- 哪项缺失信息最可能改变推荐结果。
- 下一轮应该只询问什么。
- 最近消息之间是否存在需要确认的矛盾。

它不能负责：

- 判断用户是否说谎。
- 进行心理、医疗、智力或人格诊断。
- 绕过 Java 校验直接写数据库。
- 自己编造画像事实。
- 在用户不愿回答时无限追问。

### 本地决策守卫

`ProfileDecisionValidator` 校验 Agent 输出结构和基本一致性；`ProfileReadinessPolicy` 在模型接口失败、超时或输出不合法时提供确定性兜底。

长期应保留守卫和兜底，即使以后换成自研模型。

### 检索与推荐

Embedding 模型只负责把文本转换为向量。未来的用户画像模型不会替代 Embedding，也不会直接替代 Qdrant。

初期推荐流程：

1. 从画像生成检索查询。
2. 使用相同 Embedding 模型生成查询向量。
3. 在 Qdrant 使用 Cosine 相似度召回候选策略。
4. 使用适合人群、来源、审核状态和曝光范围过滤。
5. 使用简单规则综合相似度与推荐度排序。
6. 将候选 chunk 交给聊天模型组织成最终回复，并附带来源。

有足够反馈数据后，独立的排序模型可以替换第 5 步，但不替换 Embedding 和向量召回。

第 4 步同时是「渐进投放」的唯一实现位置：审核通过不等于对全部用户可见，新入库策略先只对少量用户曝光，反馈达标后才扩大范围（见《用户投稿与渐进投放》）。

当前实现状态：第 4 步已落地为 `StrategyGovernanceService`，位置在**召回之后、按策略补齐 chunk 之前**——被挡下的策略连它的其他 chunk 也不应该被拉回来送给模型。第 5 步（排序）仍只有向量相似度，合成分 `overall_score` 已算出并落库，但**尚未参与排序**，这是有意的：升降权先用确定性规则跑通闭环，排序模型等有真实反馈数据再谈。

两个尚未生效的部分必须说清楚：

1. `app.governance.review-gate` 默认 `false`，因此“未审核”与“曝光人数上限”两条规则目前**不拦截**。现存 13 个策略档案全是 `draft`，直接开启会把推荐过滤成全空。与审核无关的三条（无源档案、已被真实反馈证伪、人工暂停）永远生效。
2. 档位状态机 `seed`(20 人) → `scaling`(`exposure_cap`) → `full` 的代码已写，但从未被真实触发过：没有任何策略累计到 20 个曝光用户，且升档判定还依赖闸门开启后的人数上限。

闸门查询失败时 fail-closed（挡下全部候选，宁可这次不推荐也不能把未审核内容当作已审核推给用户）；曝光记录失败时 fail-open（推荐已经生成，不能因为记账写不进去就丢掉它）。两条路径都打完整异常栈，因为外层包装的 message 只有一句“数据库操作失败”，真正的 SQL 错误在 `cause` 里——这个坑真实踩过一次：一个只在带范围查询时才出现的 SQL 语法错误被 best-effort 的 catch 吃掉，表现只是“曝光表一直是空的”。

### 学习策略适合人群预测模型

该模型用于完善知识库中的学习策略元数据，主要处理新增或信息不完整的学习方法，尤其是用户投稿的自由文本——投稿不带整理好的结构化字段，需要模型先抽取再交由 Java 切块。

```text
学习策略名称、原理、具体步骤和来源
  -> 适合人群预测模型
  -> 候选人群标签、适用问题、限制条件、置信度和依据
  -> 模型同时输出结构化策略字段，由 Java 按固定模板确定性切 chunk
  -> Java Schema 校验
  -> 人工审核（用户投稿一律人审，不设自动通过通道）
  -> 写入策略元数据
  -> Embedding 向量化并进入 Qdrant
  -> 先小范围投放，按真实反馈调整推荐度
```

审核通过之后直到进入 Qdrant 为止是全自动流程，不再需要人工干预。

建议输出至少包含：

- `audienceTags`：适合人群标签。
- `problemTags`：主要解决的学习问题。
- `constraints`：不适合的情况或使用前提。
- `predictedScore`：模型给出的初始推荐分。
- `confidence`：对本次预测的置信度。
- `evidence`：来自策略正文或来源的判断依据。
- `modelVersion`：生成预测的模型版本。
- 结构化策略字段：`name`、`summary`、`steps`、`suitableFor`、`notSuitableFor`，供 Java 切块使用。

`reviewStatus` 的取值已统一。历史上 `data/strategies/*.json` 全部 13 个文件用 `draft`，而本节曾定义 `pending`/`approved`/`rejected`，两套取值零交集——按文档写筛选条件会一条都查不出来。V6 迁移的 `strategies_review_status_check` 取两者并集并补上 `archived`，共五个值：`draft` / `pending` / `approved` / `rejected` / `archived`。导入时种子策略保持档案里的 `draft`，**不自行提升为 `approved`**：那是伪造审核决定，而审核者身份本身还是待定参数。

**chunk 由 Java 生成，不由模型生成。** `chunkId` 依赖 `uuid5(固定命名空间, "{strategyId}:{chunkType}:{index}")` 确定性推导，这是重复入库不产生 Qdrant 孤儿点的前提。模型直接生成 chunk 会破坏幂等性，并使 chunk 文体与既有语料不一致而损害检索质量，还会让 `RecommendationValidator` 的 `citations` 校验失去稳定锚点。模型只负责输出结构化字段，切块套用现有四类模板：`definition`、`procedure`、`suitable_condition`、`unsuitable_condition`。

它与其他模型的职责不同：

| 模块 | 核心输入 | 核心输出 | 作用阶段 |
| --- | --- | --- | --- |
| 用户画像模型 | 用户消息、历史画像（带来源层级）、过往询问策略及结果；v1 不含行为观测 | 画像更新、自述失真觉察、验证式询问策略、充分性判断 | 用户对话侧 |
| 适合人群预测模型 | 学习策略正文和来源 | 该策略通常适合的人群标签 | 知识库入库侧 |
| Embedding 模型 | 文本 | 向量 | 入库与检索侧 |
| 推荐排序模型 | 用户画像和候选策略 | 针对当前用户的候选顺序 | 在线推荐侧（远期未立项；当前排序用确定性规则：Wilson score + 最小反馈门槛 + 曝光人数上限） |

适合人群预测模型不能替代 Embedding。它生成有业务含义的结构化元数据，Embedding 仍负责语义向量化。它也不直接替代推荐排序模型：一种方法“通常适合某类人”，不代表它一定是当前用户候选中的最佳方案。

### 推荐度字段与写入者

关键不在于字段数量，而在于**每个字段只能有一个写入者**——只要写入者唯一，用户反馈就不会覆盖模型初判，模型版本之间也才可比较。V6 已把下表落成 `strategies` 的列，并指定了实际写入者：

| 字段 | 含义 | 唯一写入者 | 写入时机 |
| --- | --- | --- | --- |
| `evidence_score` | 文献证据强度；用户投稿天然低 | 导入器与审核者 | 按来源类型确定；导入器只在 `review_status='draft'` 时覆盖 |
| `effectiveness_score` | 方法本身的有效性评价 | 审核者，将来是适合人群预测模型 | 审核时确定；同上守卫 |
| `community_score` | 社区验证度 = 有用率的 Wilson 95% 置信下界 | `StrategyGovernanceService` | 反馈变化时重算，不足 10 条不动 |
| `tried_count` | 实际尝试过的人数（只计 `tried=true`） | `StrategyGovernanceService` | 同上 |
| `helpful_count` | 认为有效的人数（只计 `outcome='helpful'`，`partial` 不算） | `StrategyGovernanceService` | 同上 |
| `overall_score` | 合成总分 = 0.3×证据 + 0.5×社区 + 0.2×有效性 | `StrategyGovernanceService` | 同上 |
| `exposed_user_count` / `exposure_state` / `pending_archive` | 投放状态，从 `strategy_exposures` 与反馈推导 | `StrategyGovernanceService` | 同上 |
| `reviewer_score` | 审核者自己的判断，可空 | 审核界面（尚未实现） | 审核时确定 |

除 `evidence_score` / `effectiveness_score` / `reviewer_score` 外全是**派生值**，应用启动时从 `method_trial_feedback` 与 `strategy_exposures` 整体重建一次。公式只存在 `StrategyGovernanceService` 一处，导入器与人工改分都不自己算，避免同一公式被复制成两份而逐渐走偏。这也意味着删掉派生列的内容不是事故，重启就能恢复。

针对具体用户的临时排序分属于在线推荐阶段，不落入上表任何字段。

审核界面必须**同时展示模型给出的 `predictedScore`，并单独记录审核者自己的判断**。两者的差值就是适合人群预测模型最重要的训练标签；若共用一个字段，审核动作会覆盖模型初判，标签即被销毁。这就是 `reviewer_score` 单独开一列而不复用 `overall_score` 的原因。

此前记录的缺口已补齐：`tried_count`/`helpful_count` 现在由反馈提交触发重算（同事务内），`community_score` 与二者的换算关系已定义（Wilson 下界 + 最小样本量 10），Java 侧不仅读取而且把它们接成了运行时闸门。

仍然缺的：`reviewer_score` 无写入者（审核界面未实现）；`effectiveness_score` 目前只从档案导入，没有审核者也没有模型写它；`overall_score` 已落库但未参与排序。

此前本节曾建议 `predictedBaseScore`/`editorScore`/`feedbackScore`/`rankingScore` 四分体系，与数据实际字段不一致且未落地。四分体系并非错误，但它描述的职责已由上表承担；保留两套只会造成写入者不清。本节以数据库实际列为准。

## 用户投稿与渐进投放

知识库的主体内容来自用户投稿，而不是权威文献。原因是学习方法的正规研究文献极难获取，而项目的初心是让经过验证的好方法被传承下来。

权威文献（如 Dunlosky 等人 2013 年的综述）定位为**冷启动种子语料**：作用是让早期用户第一次使用就能得到有用的推荐，从而愿意贡献自己的方法；同时它 `evidenceScore` 高、可直接通过审核，为用户投稿提供同台竞争的对照基线。它不是内容主体。

### 投稿流程

```text
用户在 Web 界面提交自己的学习方法
  -> 模型初判：抽取结构化字段、预标注适合人群与推荐度
  -> Java 确定性切 chunk 并做 Schema 校验
  -> 进入待审核队列
  -> 人工审查：看方法本身、适合人群、模型生成的推荐度
  -> 驳回：记录原因，不入库
  -> 通过：全自动 Embedding 并写入 Qdrant，不再人工干预
  -> 小范围投放
  -> 按真实反馈调整推荐度
  -> 反馈持续偏低：进入待归档审查
```

用户投稿**一律经过人工审查，不设自动通过通道**。

人工审查只能过滤明显不合理的内容，方法是否真正有效必须靠投放后的真实反馈验证——这正是“审核通过”不等于“全量投放”的原因，也是本系统与普通内容审核的关键区别。

投稿没有权威来源，但入库流程硬校验 `sourceIds` 不能为空，因此需要新增一类来源（如 `user_submission`），其 `evidenceScore` 固定为低值。这也对应“正规来源中的明确描述优先于模型预测”的原则。

### 渐进投放

新入库策略先只对少量用户曝光，反馈达标后逐步扩大范围；反馈持续偏低则降权，低到一定程度进入待归档审查。

该机制只能在检索侧的元数据过滤层实现，因此召回必须带上审核状态与曝光范围条件。

**归档必须是软删除**：PostgreSQL 中保留完整记录并转为归档状态，仅从 Qdrant 移除向量以停止投放，并保留人工恢复入口。两个理由：

1. 被降权归档的投稿是适合人群预测模型最有价值的**负样本**。只学过成功案例的模型无法判断“看起来合理但实际无效”的方法。
2. `chunkId` 为确定性推导，硬删后同样内容重新投稿会生成相同 ID 并与历史记录冲突。

当前实现：社区分 < 0.3 且样本 ≥ 10 条时置 `pending_archive = true`，闸门无条件挡下它（与 `review-gate` 开关无关）。**没有任何代码删除数据**，也没有从 Qdrant 移除向量——停止投放靠的是检索侧闸门，效果等价但向量仍在。人工确认与恢复入口、以及 `review_status` 转 `archived` 的写入路径都尚未实现。

### 待定参数

已定并已落地的：

- **曝光机制**：按曝光人数上限。优势是能明确知道“样本已收齐、可以判断了”。`strategy_exposures` 以 `(strategy_id, user_id)` 为主键去重，否则重复推荐会把上限刷爆。
- **最小反馈门槛**：10 条。低于此值只累积不调整社区分。
- **小样本估计**：Wilson 95% 置信下界，不用裸比率。
- **归档**：系统只标记 `pending_archive`，**必须人工确认**才真归档。
- **执行后反馈档位**：已实现为 `method_trial_feedback`，是升降权的唯一依据；`adopted`/`dismissed` 已退役。
- **升权与降权速度是否不对称**：目前对称（同一个 Wilson 下界同时驱动升档与待归档），但下界本身对失败更敏感：10/20 的下界约 0.30 刚好卡在 `LOW_COMMUNITY` 上，而 5/10 约 0.24 会直接进待归档。

仍未定：

- 投稿者能否查看自己投稿的状态与被采纳次数。这对投稿意愿是强激励，也最贴合传承的初心。`strategies.submitted_by` 已预留，但无查询接口。
- 审核权限在哪一层强制。角色本身已定（V9 的 `access_codes.role`，`tester` / `reviewer`，由 `redeem` 返回），但没有审核端点去校验它，所以 `reviewer` 当前只是身份告知；`strategies.reviewed_by` 仍只是个无人写入的 `VARCHAR(64)`，也没定下写访问码还是写 `label`。这直接卡住了 `review-gate` 能否开启。
- 按比例随机曝光或按用户分群是否需要。当前只有人数上限，命中哪些用户完全由向量相似度决定，不是随机分配——这会引入选择偏差（只有画像匹配的人才被曝光），将来做统计推断时必须考虑。

### 已知风险

**冷启动的双边市场问题**：库内容少 -> 推荐质量差 -> 用户不愿投稿 -> 库仍然少。种子语料必须先于投稿功能就绪。

**审核工作量会成为吞吐瓶颈**：投稿一律人审。V9 起可以发放 `reviewer` 角色的访问码，但审核端点未实现，实际审核者数量仍为一。每条投稿需要判断方法、适合人群与模型推荐度是否有依据，投稿量上升后人工审核会先于技术能力达到上限。审核界面需为此优化（预填模型判断、批量操作），并考虑限制投稿速率。

**投稿接口是成本放大攻击面**：`AccessCodeFilter` 仅拦截 `^/api/v1/users/([^/]+)(?:/.*)?$`。若投稿接口命名为 `/api/v1/strategies/**`，则完全不受访问码保护，公网部署后任何人可提交并触发模型初判，刷爆 API 预算并用垃圾淹没审核队列。对策：投稿接口纳入 `/api/v1/users/{externalId}/` 前缀以复用现有过滤器；模型初判不在提交时同步执行，改为队列或审核者点开时触发；加投稿频率限制。

**小样本噪声会误杀好方法**：“少量投放”与“靠反馈升降权”组合会自然产生该问题。若投放给 5 人而前 2 人恰好都觉得没用，裸比率为 0%，一个好方法会在拿到任何有意义的数据之前被判死刑。已采取的对策：最小反馈门槛 10 条、Wilson 下界而非裸比率。**未采取“增量更新而非重算”**：当前每次反馈都从 `method_trial_feedback` 全量重算该策略的计数。这是有意的取舍——重算幂等、可从源数据完全重建（已验证：清空反馈表后重启，13 个策略的派生值全部回到正确基线），而增量累加一旦丢一次事件就永久偏差。策略总数在可预见未来不会大到让单策略重算成为瓶颈；真到了那一步，该优化的是聚合查询而不是换成累加。

## 用户画像的数据层级

未来画像不能把所有信息都当成同等可靠的事实，建议至少区分：

| 层级 | 含义 | 示例 |
| --- | --- | --- |
| `explicit` | 用户明确表达 | “我每天只有 30 分钟” |
| `observed` | 系统从真实行为记录得到 | 连续三次未完成一小时计划 |
| `inferred` | 模型根据证据提出的待确认假设 | 可能更适合短时学习任务 |
| `confirmed` | 用户确认过的信息或推测 | 用户确认每天只能学习 30 分钟 |
| `conflicting` | 新旧证据暂时冲突 | 曾说 30 分钟，后来表示工作日有 2 小时 |

`inferred` 不能悄悄升级成事实。影响明显的推测应向用户确认；确认结果写入 `confirmed` 层级，而不是覆盖原字段值。

`observed` 层级现在**只存在采集侧，不存在使用侧**。`behavior_observations` 表已落地，由确定性代码从本库已有数据算出（不含任何模型判断），在写入行为的事务提交之后重算。按 2026-09-10 定下的隐私范围，v1 的模型一只看对话相关内容（当前消息、历史画像、过往询问策略及结果），**`observed` 不进入它的输入**。采集与使用解耦：现在照采照存，目的只是将来评估“自述失真觉察”到底做不做得起来时手上有对照面，而不是等到那天才开始攒数据。真要接入时也只给已经聚合好的偏差信号（如“自述每天 60 分钟 vs 近 7 天实际活跃 1 天”），不给原始行为日志。用户对隐私敏感，采集范围必须小于使用范围时才敢长期留着。

两个比率的分子分母量级必须一致：`method_trial_feedback` 有 `UNIQUE (user_id, strategy_id)`，反馈数天然是去重后的方法数，所以跟进率的分母用“被推荐过的不同方法数”而不是推荐消息数——一条消息里通常有好几个方法，拿消息数当分母会让“率”超过 1。这类错误不会报错，只会静默地产出一个看似合理的脏指标。

用户可以查看画像，但**不提供直接编辑或更正字段的入口**。理由是产品的核心策略为“信用户的话只信一半”：用户可能对自己的定位不清晰，画像应由模型基于行为与多轮对话逐步引出；开放手动编辑等于完全采信用户自述，与该策略直接冲突。据此取消 roadmap 阶段 5 中“允许用户更正画像信息”一项。注意这与来源层级不矛盾：模型推测经用户确认是允许的，用户不能直接改写字段值。

## 模型边界与替换方式

当前第三方聊天模型承担两个不同任务：

1. 从当前消息提取画像更新。
2. 根据画像和对话决定追问或推荐。

两个任务应保持独立接口，即使暂时使用同一个模型。未来自研用户画像模型只要遵循稳定的输入输出 JSON 契约，就可以替换这两个调用，而不需要重写 PostgreSQL、Java Repository、Qdrant 或 Web 页面。

模型一的职责不止“提取 + 追问”，经 2026-09-10 确认为四项：画像判别与更新、自述失真觉察、验证式询问策略生成、充分性判断（详见 roadmap 阶段 9）。其中询问策略由模型一生成、**措辞由聊天模型负责**——因此替换时须把现有 `ConversationalProfileAgent`（判断与措辞混合在一个类）拆成两层：模型一出策略与意图，聊天模型把策略变成无害、自然的人话。这层措辞同时是信任防线：模型怀疑用户自述，但用户不应感到被套话。

推荐排序是另一个目标不同的模块。它的输入是用户画像和候选学习策略，输出是候选顺序或分数；不建议与对话画像模型强行合并。**当前不做排序模型**：渐进投放的升降权与候选顺序由确定性规则承担，可解释、可审计；是否引入学习型排序待有足够真实数据后再议。

适合人群预测也是独立任务。早期可以继续使用聊天模型配合严格 JSON Prompt 生成预标注；积累足够人工确认的数据后，再接入自己的深度学习模型。替换时应保持输入输出契约不变，让知识库处理代码不依赖某个具体模型。

## 未来后端边界

建议 Spring Boot 层逐步形成以下服务：

- `ConversationService`：会话与消息生命周期。（未拆分，目前在 `UserProfileService` 与三个 Repository 里）
- `UserProfileService`：抽取、校验、合并和画像历史。（已存在，历史版本未做）
- `ProfileDialogueService`：充分性判断、冲突确认和追问。（未拆分，目前是 `ConversationalProfileAgent` + `ProfileDecisionValidator` + `ProfileReadinessPolicy`）
- `StrategyRetrievalService`：Embedding、Qdrant 召回和过滤。（未拆分，目前在 `RecommendationService` 里）
- `RecommendationService`：排序、答案生成、引用和结果保存。（已存在，排序未做）
- `FeedbackService`：用户反馈与效果数据。（已存在，只管 👍；尝试后反馈在 `RecommendationHistoryService`）
- `StrategyGovernanceService`：推荐闸门、曝光去重、反馈升降权。（已存在）
- `BehaviorObservationService`：行为观测采集。（已存在）
- `ModelCallLogger`：模型调用日志的唯一写入入口，负责脱敏与保留期。（已存在）
- 尚未有：投稿受理与审核队列服务。

这里的拆分建议不是目标本身。当前 `RecommendationService` 同时管召回、闸门、补齐、生成与校验，职责偏重；但只有一个人维护时，过早拆分会把一条可读的链路打散到六个文件里。真正已经守住的是两个边界：脱敏与保留期收敛到 `ModelCallLogger` 一个入口（不靠调用方自觉），派生分数的公式收敛到 `StrategyGovernanceService` 一处（不靠约定）。

Web 前端只调用后端 API，不直接访问 SiliconFlow、Qdrant 或 PostgreSQL。

## 安全、隐私与可观察性

- API Key 和数据库密码只通过环境变量或服务端密钥管理加载。
- 日志不记录密钥。`model_call_logs.input_json` 曾直接存用户逐字说过的原话（`extract` 任务的 `currentUserMessage`），是全项目最大的隐私暴露面；现在写入前经 `ModelCallSanitizer` 脱敏，替换证件号、银行卡号、手机号、邮箱与 8 位以上连续数字，并保留学习相关的短数字（它们正是画像要抽的字段值，误伤就等于毁掉训练数据）。脱敏放在写入的唯一入口而不是靠调用方自觉，因为新增一处日志调用时忘了脱敏就是真的泄露。
- 姓名、学校、住址这类没有固定格式的信息正则处理不了，**不假装已解决**，只能靠保留期兜住：`app.logs.retention-days` 默认 365 天，启动时清一次并按 cron 定时清。不按 `status` 区分保留期，因为 `fallback` 与 `failed` 是最有价值的难样本。`user_id` 外键是 `ON DELETE SET NULL`，删用户会自动匿名化它的日志。
- 脱敏只作用于日志，`messages.content` 保留原文：用户自己的消息历史不应该被系统改写。脱敏函数返回深拷贝而不改入参，因为调用方记完日志还要继续用原对象做校验与合并，原地修改会把占位符带进画像。
- 行为观测采集范围小于使用范围（只存不喂模型），且采集失败一律只打印不抛出，任何情况下不能让对话或反馈提交失败。
- 用户应能知道画像用于什么，并能查看或删除自己的画像数据。删除属隐私权利，与“不提供字段编辑入口”不冲突。删除入口尚未实现；目前只有数据库层的 `ON DELETE CASCADE` 保证删用户会带走它的会话、消息、画像、反馈与观测。
- 保存模型版本、决定结果、置信度、回退原因和耗时，方便评测与排错。Prompt 版本尚未入库，目前只能从代码里的常量反推，这让“换个 Prompt 后质量变了吗”无法回答。
- 对超时、限流、JSON 不合法和数据库失败分别处理，不能把技术故障伪装成用户信息不足。推荐链路超时确实会发生：`RecommendationChatClient` 的 `readTimeout` 是 90 秒，同一条链路 2026-09-10 用了 23.2 秒（prompt 3427 / completion 845），2026-09-11 用了 83.9 秒（prompt 3410 / completion 893），早期探针还出现过一次 90.5 秒真超时。V8 起三个 token 计数入库，这构成了一组同负载对照：输入差 0.5%、输出差 5.7%、耗时差 3.6 倍，变量只剩服务端生成速率（实测 10-36 token/秒，两天的同批 `extract`/`decide` 各自内部速率一致）。结合输入更大的那次反而更快，可以定下：耗时几乎全由 completion 决定而数千 token 的输入贡献不到一秒。因此超时风险是“输出上限乘以服务端速率波动”而不是知识负载过大；按实测下限算 `max_tokens=1400` 需要 140 秒，单靠调阈值补不回来。超时被归为 `failed` 并记下 `error_message`，画像对话流程不受影响。
- 同一原则也适用于静默截断：推荐时把命中策略的全部 chunk 补齐（`QdrantClient.findByStrategyIds`）曾固定只取第一页 100 个，超出部分无错误无日志地丢掉，模型会拿着半个策略的资料给出看上去完全正常的推荐。现在分页取回并设上限 200，命中总数与实际取回数的差值记在 `model_call_logs` 的 `knowledgeDropped`，与已有的 `gateFilteredOut` 并列：推荐质量下降时能区分“闸门挡的”“预算截断的”与“知识库本来就薄”。
